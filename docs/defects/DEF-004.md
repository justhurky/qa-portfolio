# DEF-004 A malformed request body bypasses the error contract

| | |
|---|---|
| **Severity** | Major |
| **Priority** | Medium |
| **Status** | Open |
| **Found in** | Ground Station Booking 1.0.0 |
| **Found by** | Exploratory session [EX-04](../../manual-tests/exploratory-charters.md) |
| **Requirement** | [REQ-53](../requirements.md), [REQ-60](../requirements.md), [REQ-64](../requirements.md) |
| **Covered by** | `IT-68b`, `IT-68c`, both tagged `KnownDefect` |

## Summary

Every documented error carries a machine readable `error.code`. A body that fails JSON
deserialisation does not: the request never reaches the handler, so the framework answers instead.
What the client then receives depends on the hosting environment, and neither answer is the
documented one.

## Steps to reproduce

As `operator-key`, post a body that is not a JSON object:

```bash
curl -i -X POST http://localhost:5000/api/bookings \
  -H 'X-Api-Key: operator-key' -H 'Content-Type: application/json' \
  -d '{broken'
```

Repeat with `[]` and with `"text"`.

## Actual result

| Environment | Response |
|-------------|----------|
| Production | `400` with a **completely empty body**. No code, no message. |
| Development | `400` carrying a **full `System.Text.Json` stack trace**, naming internal types and call frames. |

## Expected result

```json
400
{ "error": { "code": "MALFORMED_JSON", "message": "Request body is not valid JSON" } }
```

in both environments, with no internal detail in either.

## Analysis

Minimal API parameter binding deserialises the body before the handler runs. When that throws,
the failure is handled by the framework, which knows nothing about this application's error shape.
The handler, and with it `Error(...)`, is never reached.

The environment dependence is the part worth noting. Probing the running service gave the empty
body; the in-process integration tests, which default to the Development environment, gave the
stack trace. Testing a single configuration would have shown one half and hidden the other, and
the hidden half is the one with the information disclosure risk.

## Impact

Clients cannot distinguish a malformed body from any other 400, because there is nothing to
distinguish it by. A retry loop has no signal that retrying is pointless. If the service is ever
deployed with the Development environment set, which is a one line mistake in a container
definition, every malformed request returns internal type and call stack information.

## Suggested fix

Take the body as a raw stream or a `JsonDocument` and deserialise inside the handler, so a failure
is caught and answered through the same path as every other error:

```csharp
app.MapPost("/api/bookings", async (HttpContext context, ...) =>
{
    CreateBookingRequest? request;
    try
    {
        request = await context.Request.ReadFromJsonAsync<CreateBookingRequest>();
    }
    catch (JsonException)
    {
        return Error(400, "MALFORMED_JSON", "Request body is not valid JSON");
    }
    ...
});
```

An exception handling middleware that converts any unhandled exception into the documented shape
would cover REQ-64 at the same time.
