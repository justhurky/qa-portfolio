# DEF-001 An emergency booking can be created entirely in the past

| | |
|---|---|
| **Severity** | Major |
| **Priority** | High |
| **Status** | Open |
| **Found in** | Ground Station Booking API 1.0.0, commit at the time of writing |
| **Found by** | Exploratory testing of the priority override rule, then confirmed by TC-38 |
| **Requirement** | [REQ-28](../requirements.md) |
| **Covered by** | `BookingSchedulingTest.emergencyMayNotBeBackdated`, tagged `known-defect` |

## Summary

`EMERGENCY` priority is documented as exempt from the 15 minute minimum lead time so that an urgent
pass can start immediately. The implementation does not relax the lower bound, it removes it
entirely, so a supervisor can create a booking whose window closed days or years ago.

## Steps to reproduce

1. Reset the system under test: `POST /api/test/reset`.
2. As `supervisor-key`, send:

```http
POST /api/bookings
X-Api-Key: supervisor-key
Content-Type: application/json

{
  "stationCode": "PER",
  "purpose": "Backdated emergency",
  "startsAt": "2026-10-13T18:13:23Z",
  "endsAt": "2026-10-13T18:43:23Z",
  "priority": "EMERGENCY"
}
```

The two timestamps are three days before the current time.

## Actual result

`201 Created`. The booking is stored in state `REQUESTED` with the past window, appears in
`GET /api/bookings`, and can be confirmed and completed afterwards. The same request with
`startsAt` one year in the past is also accepted.

## Expected result

`422 Unprocessable Entity` with `error.code` `LEAD_TIME_TOO_SHORT`. REQ-28 permits an emergency
booking to start immediately; it does not permit one to start before now.

## Analysis

In `sut/server.js` the lead time check is guarded by the override flag:

```
if (!rule.mayOverrideLeadTime && lead < domain.MIN_LEAD_MINUTES) { ... }
```

When `mayOverrideLeadTime` is true the whole comparison is skipped, including the implicit
`lead >= 0` part of it. The upper bound of 30 days is still enforced for every priority, which is
why the asymmetry was not obvious from reading the code.

## Impact

The schedule can contain bookings that could never have been executed. Anything that reasons over
the schedule is affected: capacity accounting counts a past slot as occupied, operators see entries
they cannot act on, and a completed booking with a window in the past is indistinguishable from a
real historical record. There is also an audit concern, because a supervisor can insert a plausible
looking record of a pass that was never planned.

## Suggested fix

Give the override a floor instead of removing the check:

```
const minimumLead = rule.mayOverrideLeadTime ? 0 : domain.MIN_LEAD_MINUTES;
if (lead < minimumLead) { ... }
```

## Notes

Found while probing the boundaries of the override rule rather than the rule itself. The decision
table in [test-design.md](../test-design.md) has the override as rule R8, and asking "what is the
other side of this boundary" is what surfaced it.
