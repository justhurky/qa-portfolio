# DEF-001 An emergency booking can be created entirely in the past

| | |
|---|---|
| **Severity** | Major |
| **Priority** | High |
| **Status** | Open |
| **Found in** | Ground Station Booking 1.0.0 |
| **Found by** | Exploratory session [EX-01](../../manual-tests/exploratory-charters.md) |
| **Requirement** | [REQ-28](../requirements.md) |
| **Covered by** | `UT-15` (unit), `IT-35` (integration), both tagged `KnownDefect` |

## Summary

`EMERGENCY` priority is documented as exempt from the 15 minute minimum lead time so that an urgent
pass can start immediately. The implementation does not relax the lower bound, it removes it, so a
supervisor can create a booking whose window closed days or years ago.

## Steps to reproduce

1. `POST /api/test/reset`
2. As `supervisor-key`, create a booking with `priority: "EMERGENCY"` whose `startsAt` and `endsAt`
   are three days in the past.

```http
POST /api/bookings
X-Api-Key: supervisor-key
Content-Type: application/json

{ "stationCode": "PER", "purpose": "Backdated emergency",
  "startsAt": "2026-10-14T09:00:00Z", "endsAt": "2026-10-14T09:30:00Z",
  "priority": "EMERGENCY" }
```

## Actual result

`201 Created`. The booking is stored in state `REQUESTED` with its past window, appears in the
schedule, and can be confirmed and completed afterwards.

## Expected result

`422 Unprocessable Entity` with code `LEAD_TIME_TOO_SHORT`. REQ-28 permits an emergency to start
immediately; it does not permit one to start before now.

## Analysis

`BookingRules.CheckLeadTime` guards the whole comparison with the override flag:

```csharp
if (!RolePolicy.MayOverrideLeadTime(priority) && lead < MinLeadMinutes)
```

When the flag is true the comparison is skipped entirely, including the implicit `lead >= 0` part
of it. The upper bound of 30 days is still enforced for every priority, which is why the asymmetry
is not obvious from reading the code: the rule is bounded above but not below.

## Impact

The schedule can hold bookings that could never have been executed. Capacity accounting counts a
past slot as occupied, operators see entries they cannot act on, and a completed booking with a
past window is indistinguishable from a genuine historical record, which is an audit problem as
much as a scheduling one.

## Suggested fix

Give the override a floor instead of removing the check:

```csharp
double minimumLead = RolePolicy.MayOverrideLeadTime(priority) ? 0 : MinLeadMinutes;
if (lead < minimumLead) { ... }
```

`UT-15` already asserts the expected behaviour, so it will turn green when the fix lands.
