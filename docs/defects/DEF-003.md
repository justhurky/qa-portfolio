# DEF-003 The API rejects the priority values it returns

| | |
|---|---|
| **Severity** | Critical |
| **Priority** | High |
| **Status** | **Fixed**, regression test in place |
| **Found in** | Ground Station Booking 1.0.0 |
| **Found by** | Exploratory session [EX-02](../../manual-tests/exploratory-charters.md) |
| **Requirement** | [REQ-26](../requirements.md), [REQ-53](../requirements.md) |
| **Covered by** | `UT-60` to `UT-66`, in particular the round trip property in `UT-65` |

## Summary

The API refused the documented priority value `ROUTINE` and accepted only the undocumented
`Routine`, while returning `ROUTINE` in every response. A client could not send back the value it
had just received, and the web interface, whose dropdown submits `ROUTINE`, could not create a
booking with an explicit priority at all.

## Steps to reproduce

As `operator-key`, post an otherwise valid booking with `"priority": "ROUTINE"`.

## Actual result

```json
400
{ "error": { "code": "VALIDATION_FAILED",
             "message": "priority must be one of ROUTINE, PRIORITY, EMERGENCY",
             "details": { "field": "priority" } } }
```

The message lists exactly the value that was sent. Sending `"Routine"` instead returned
`201 Created` with `"priority": "ROUTINE"` in the body.

## Expected result

`201 Created` for the documented values, and a refusal for anything else.

## Analysis

The endpoint parsed the field with `Enum.TryParse(request.Priority, ignoreCase: false, out priority)`
against a C# enum whose members are `Routine`, `Priority` and `Emergency`, while the response
rendered the same value through `ToUpperInvariant()`. Reading and writing used two different
vocabularies, and nothing connected them.

Two things made it invisible for a while. The error message was generated from the documented
values rather than from the ones actually accepted, so it described a contract the code did not
implement. And the integration tests had been written with C# style values, because that is what
the enum looks like from inside the test project, so the suite asserted the implementation's
behaviour instead of the specification.

## Impact

The web interface could not create a booking with any explicit priority, so the primary user flow
was broken. Any API client following the documentation was equally broken, and a client that read
a booking and wrote it back could never succeed.

## Fix

The wire vocabulary now lives in one place, `PriorityWire`, which both parses and renders, so the
two directions cannot drift apart again. The error message is generated from the same list the
parser uses.

```csharp
if (!PriorityWire.TryParse(request.Priority, out Priority priority))
{
    return Error(400, "VALIDATION_FAILED",
        $"priority must be one of {string.Join(", ", PriorityWire.All)}", ...);
}
```

## Regression test

`UT-65` does not assert a list of literals, which would have been just as easy to get wrong a
second time. It asserts the property that matters:

```csharp
foreach (Priority priority in Enum.GetValues<Priority>())
{
    string wire = PriorityWire.ToWire(priority);
    Assert.True(PriorityWire.TryParse(wire, out Priority parsed),
        $"the API renders {priority} as {wire} but will not accept it back");
    Assert.Equal(priority, parsed);
}
```

Adding a new priority without wiring both directions now fails the build. The integration tests
were also rewritten to use the documented values, so they test the contract rather than the code.
