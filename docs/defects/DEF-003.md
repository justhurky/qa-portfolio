# DEF-003 An oversized request body closes the connection instead of answering 413

| | |
|---|---|
| **Severity** | Major |
| **Priority** | Medium |
| **Status** | Open |
| **Found in** | Ground Station Booking API 1.0.0 |
| **Found by** | TC-80, while checking the documented payload limit |
| **Requirement** | [REQ-61](../requirements.md), [REQ-53](../requirements.md) |
| **Covered by** | `QueryAndRobustnessTest.oversizedBodyIsRefused`, tagged `known-defect` |

## Summary

A request body above the 64 KiB limit is supposed to be answered with `413 PAYLOAD_TOO_LARGE`.
Instead the server destroys the socket, so the client never receives an HTTP response at all and
sees a transport error.

## Steps to reproduce

1. Reset the system under test.
2. As `operator-key`, post a valid booking whose `purpose` field contains 70000 characters.

```python
body = json.dumps({"stationCode": "PER", "purpose": "x" * 70000,
                   "startsAt": "2026-12-01T10:00:00Z", "endsAt": "2026-12-01T10:30:00Z"}).encode()
urllib.request.urlopen(urllib.request.Request(url, data=body, headers=headers))
```

## Actual result

No HTTP response. The client library reports a connection level failure:

- Python `urllib`: `RemoteDisconnected: Remote end closed connection without response`
- REST Assured over Apache HttpClient: `NoHttpResponseException: 127.0.0.1:3123 failed to respond`

## Expected result

```json
413
{"error":{"code":"PAYLOAD_TOO_LARGE","message":"Request body is larger than 64 KiB"}}
```

## Analysis

In `sut/server.js` the size guard rejects the promise and then immediately calls
`request.destroy()`:

```
reject(new ApiError(413, 'PAYLOAD_TOO_LARGE', ...));
request.destroy();
```

Destroying the request tears the socket down before the rejection has been turned into a response,
so the handler that would have written the 413 never gets the chance. The intention, to stop
reading a body that is already too large, is right; the ordering is not.

## Impact

Every client sees a transport failure rather than a result it can act on. A retry loop will usually
treat a dropped connection as a transient network problem and retry, which means a client that
repeatedly posts an oversized body will hammer the service instead of failing fast with a clear
error. It also breaks REQ-53, because this is the one failure mode with no machine readable code.

## Suggested fix

Stop consuming the body without killing the connection, send the response, and only then end it:

```
request.pause();
reject(new ApiError(413, 'PAYLOAD_TOO_LARGE', 'Request body is larger than 64 KiB'));
```

and let the normal error path write the response. If the remaining bytes must be discarded, drain
them with `request.resume()` after the response has been flushed rather than destroying the socket.

## Notes

The test for this case originally failed as an error rather than an assertion failure, which is
itself the signal: an assertion failure means the system answered something unexpected, a transport
error means it did not answer at all. Worth distinguishing when triaging a red suite.
