# DEF-002 The documented 15 minute lead time boundary cannot be used

| | |
|---|---|
| **Severity** | Minor |
| **Priority** | Medium |
| **Status** | Open |
| **Found in** | Ground Station Booking API 1.0.0 |
| **Found by** | Boundary value analysis of the lead time rule, TC-33b |
| **Requirement** | [REQ-24](../requirements.md) |
| **Covered by** | `BookingSchedulingTest.leadTimeAtTheExactBoundaryIsAccepted`, tagged `known-defect` |

## Summary

REQ-24 says a booking must start at least 15 minutes from now, which makes `now + 15 minutes` a
valid input. In practice that request is always refused, because the server compares against its own
clock after the request has travelled and been parsed, by which point the gap has shrunk below the
threshold.

## Steps to reproduce

1. Reset the system under test.
2. Compute `startsAt` as exactly the current UTC time plus 15 minutes, and `endsAt` 30 minutes
   after that.
3. As `operator-key`, post the booking.

```bash
START=$(python -c "import datetime; print((datetime.datetime.now(datetime.timezone.utc)+datetime.timedelta(minutes=15)).isoformat().replace('+00:00','Z'))")
```

## Actual result

```json
422
{"error":{"code":"LEAD_TIME_TOO_SHORT",
          "message":"A ROUTINE booking must start at least 15 minutes from now",
          "details":{"leadMinutes":14}}}
```

The reported lead is 14 minutes even though 15 were requested.

## Expected result

`201 Created`. A value documented as valid should be accepted.

## Analysis

Two separate things combine here.

The comparison is `lead < MIN_LEAD_MINUTES` on a floating point number of minutes. A client that
asks for the earliest permitted slot sends a timestamp that was exactly 15 minutes ahead when it was
built; by the time the server evaluates it the gap is 14.98 minutes and the strict comparison
refuses it. The boundary is therefore not reachable by any client, only approachable.

The diagnostic makes it harder to see: `details.leadMinutes` is produced with `Math.floor`, so
14.98 is reported as 14 and the response looks as though the client asked for 14 minutes.

## Impact

Low in absolute terms, but it is the kind of defect that produces confusing support traffic. A
user interface that offers "earliest available slot" and fills in `now + 15 minutes` would fail
every time, and the error message would appear to contradict the request the user made.

## Suggested fix

Either state the rule with a tolerance and compare against it, or round the lead time to whole
minutes before comparing:

```
if (!rule.mayOverrideLeadTime && Math.round(lead) < domain.MIN_LEAD_MINUTES) { ... }
```

Separately, report the lead time with the same rounding used for the decision, so that the
diagnostic agrees with the rule that produced it.

## Notes

This is the reason the passing boundary test uses 60 minutes rather than 15: a test that sits
exactly on an unreachable boundary is flaky by construction. The boundary case is kept as its own
test, tagged, so the finding stays visible instead of being quietly rounded away.
