# DEF-002 The documented 15 minute lead time boundary cannot be used

| | |
|---|---|
| **Severity** | Minor |
| **Priority** | Medium |
| **Status** | Open |
| **Found in** | Ground Station Booking 1.0.0 |
| **Found by** | Boundary value analysis, then confirmed through the interface in [MT-02](../../manual-tests/test-cases.md) |
| **Requirement** | [REQ-24](../requirements.md) |
| **Covered by** | `IT-32` (integration), tagged `KnownDefect` |

## Summary

REQ-24 makes `now + 15 minutes` a valid start time. In practice that request is always refused,
because the server compares against its own clock after the request has been built, sent and
parsed, by which point the gap has shrunk below the threshold.

## Steps to reproduce

1. `POST /api/test/reset`
2. Compute `startsAt` as exactly the current UTC time plus 15 minutes, `endsAt` 30 minutes later.
3. As `operator-key`, post the booking.

## Actual result

```json
422
{ "error": { "code": "LEAD_TIME_TOO_SHORT",
             "message": "A Routine booking must start at least 15 minutes from now" } }
```

## Expected result

`201 Created`. A value the specification describes as valid should be accepted.

## Analysis

This is the interesting half of the defect: **the rule itself is correct, and the unit test proves
it.** `UT-12` passes `lead = exactly 15` into `BookingRules.CheckLeadTime` with an injected `now`
and the rule allows it. The unit layer cannot see the defect at all, because it has no latency.

The defect only exists once a clock and a network are involved: the client builds a timestamp that
is 15.000 minutes ahead, and by the time the server evaluates it the gap is 14.998 minutes. The
boundary is approachable but not reachable by any client.

That gap between the two layers is the point worth keeping. A rule that is provably right in
isolation can still be unusable in the product, and only a test that crosses the same boundary the
user crosses will show it.

## Impact

Low in absolute terms, but it generates confusing support traffic: an interface that offers
"earliest available slot" and fills in `now + 15 minutes` would fail every time, with a message
that appears to contradict the request. Observed from the user's side as OBS-01.

## Suggested fix

State the rule with a tolerance and compare against it, for example by rounding the lead time to
whole minutes before the comparison, so that a client asking for the documented minimum succeeds:

```csharp
if (Math.Round(lead) < minimumLead) { ... }
```
